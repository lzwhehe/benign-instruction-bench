\section{Introduction}
\label{sec:intro}

Large language model (LLM) agents read email, calendars, web pages, and transaction histories on a user's behalf, and every one of those sources can carry text written by someone else. Indirect prompt injection turns that text into instructions~\cite{greshake2023}: an attacker who can write a calendar event description, a product review, or a table cell controls part of what a tool returns, and the agent may act on it. The cheapest defense to deploy is a detector, a small classifier that screens every tool output and drops what looks like an injection~\cite{piguard,llamafirewall,promptshield}. It needs no change to the agent or the model, which is why guardrail toolkits ship detectors and agent benchmarks include one as a baseline defense~\cite{agentdojo}. A detector can fail in two ways: if it misses injected text, the agent may follow the attacker; if it is too eager, it drops ordinary tool outputs, and the agent cannot finish the user's task.

Teams choose among detectors by their scores on public benchmarks. A 2025 evaluation of nine open guardrails concluded from BIPIA's email and table tasks that PIGuard detects indirect injection effectively~\cite{mozillaguardrails}, and a 2026 comparison of detection methods on more than 300{,}000 labeled prompts found that fine-tuned models achieve the highest detection rate on balanced benchmarks~\cite{dzhaliuk2026}. Two assumptions in this practice have not been tested. First, benchmark text is not what an agent's detector screens. Agents see serialized tool outputs (records, lists, confirmations), false alarms on them translate into failed tasks, and a deployment must operate at a false-positive rate far below what balanced accuracy reflects. Second, nobody checks whether a benchmark overlaps with the detector's training data. Prior work showed that same-source splits inflate scores~\cite{benchmarkslie} and argued for low false-positive evaluation~\cite{promptshield,pidsbench}, and a community benchmark has recently scored released detectors on AgentDojo tool outputs~\cite{buriedinjections}. We are not aware of a study that evaluates released detectors on the tool outputs an agent actually screens, at a deployable operating point and across independently built benchmarks, together with an audit of their training data. This study addresses that gap.

We evaluate fifteen released detectors, from 2023 DeBERTa classifiers through Meta's Prompt Guard~2 to 2026 models built for agent inputs, and two task-aware LLM judges on the tool outputs of two agent benchmarks, AgentDojo~\cite{agentdojo} and $\tau$-bench~\cite{taubench}, and on the injection benchmark BIPIA~\cite{bipia}. This study proposes no new detector; it is a measurement study whose contribution is an evaluation methodology for deployed detectors and the evidence it produces (Fig.~\ref{fig:overview}). The measurement requires three things that existing benchmarks do not provide: benign agent tool outputs with certain ground truth, which we obtained by replaying the benchmarks' ground-truth tool calls without any LLM; reliable labels for injected outputs, which we obtained by differential replay against the clean environment, because substring matching fails on serialized outputs; and a link from performance to training data, which we obtained by auditing the published training data of two detectors against all three benchmarks and against the attacks of InjecAgent~\cite{injecagent}.

We address seven research questions:
\begin{itemize}
\item \RQ{1}: How often do detectors flag benign agent tool outputs, and how many tasks does that stop? (Section~\ref{sec:rq1})
\item \RQ{2}: How many injections do detectors catch at 1\% false-positive rate (FPR), and does a detector's rank on one benchmark predict its rank on another? (Section~\ref{sec:rq2})
\item \RQ{3}: Does what a detector was trained on explain where it works? (Section~\ref{sec:rq3})
\item \RQ{4}: Does knowing the user's request help, and which attack goals does each approach miss? (Section~\ref{sec:rq4})
\item \RQ{5}: Do input format and metadata change false positives? (Section~\ref{sec:rq5})
\item \RQ{6}: Do the results hold with thresholds set in advance, under sampling uncertainty, and on outputs a real agent received? (Section~\ref{sec:robust})
\item \RQ{7}: What does screening every tool output cost? (Section~\ref{sec:cost})
\end{itemize}

The results reverse what a benchmark-based comparison would conclude. PIGuard catches \BIPGTpr of BIPIA injections at 1\% FPR but only \ADPGTpr of AgentDojo injections. Between the two agent benchmarks, rankings agree only partly (Kendall's $\tau=\TauADTB$, not significant), whereas false-positive rates on tool outputs, which range from none to over 90\%, agree closely ($\tau=\TauFPRADTB$). The training data explain the pattern. PIGuard was trained on \PGBipiaRows full BIPIA inputs; it also saw \NIASeen InjecAgent attacks as short prompts, yet inside $\tau$-bench tool outputs it detects them no better than unseen ones (\TBSeenPG versus \TBUnseenPG). Horizon-Labs shares no data with any benchmark, was trained on agent-style inputs, and leads both agent benchmarks (\MHZAD and \TBTprHZ) with almost no false alarms, also with thresholds calibrated on held-out suites (\LoHZTpr). Task-aware judges detect 54--78\% of injections at 1\% FPR, below the best detectors, at several times their cost.

The main contributions of this study are as follows:
\begin{itemize}
\item \textbf{An evaluation methodology for deployed detectors:} LLM-free replay for benign outputs with certain labels and a task structure, differential replay for injected outputs, and false positives reported as blocked tasks at a fixed low budget, with thresholds also calibrated on held-out suites (Sections~\ref{sec:method} and~\ref{sec:robust}). A real agent run confirmed that replay reproduces the outputs the agent receives, up to write timestamps.
\item \textbf{A cross-benchmark transfer analysis:} detection rankings do not transfer from BIPIA to AgentDojo and transfer only partly between two agent benchmarks, while false-positive behavior on tool outputs is stable (Sections~\ref{sec:rq1}, \ref{sec:rq2}, and~\ref{sec:robust}).
\item \textbf{A training-data audit of released detectors:} PIGuard's published training split contains BIPIA's training-half attacks and many of its clean contexts, and a seen/unseen comparison shows that the form of the training inputs, not overlap in attack strings, decides where a detector works (Section~\ref{sec:rq3}).
\item \textbf{Guidance for practitioners:} a seven-step procedure for selecting, calibrating, and layering detectors, each step tied to a result (Section~\ref{sec:guidelines}).
\end{itemize}

The study is limited to detectors that screen tool outputs, evaluated against the static attacks that public benchmarks ship. The remainder of this paper is organized as follows. Section~\ref{sec:background} introduces indirect prompt injection, a running example, and the threat model, and Section~\ref{sec:related} reviews related work. Sections~\ref{sec:method} and~\ref{sec:setup} describe the methodology and the experimental setup. Section~\ref{sec:results} answers the research questions, Section~\ref{sec:discussion} discusses the results, their implications, and limitations, and Section~\ref{sec:conclusion} concludes.
